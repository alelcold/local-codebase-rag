## TL;DR

- 我的地端 codebase RAG 問「玩家受傷後的無敵時間在哪裡設定？」時，取回的 4 個片段**全是 Markdown**，定義常數的 `src/config/gameConfig.ts` 一個都沒進來。
- 我先做了評估工具（`evaluate.py`，10 題主題庫 + 5 題識別字題庫 + 8 題範圍外題庫），再依序試了 7 種做法：混合檢索、分類取回、chunk metadata、prompt v2、相似度門檻、rerank、防幻覺 prompt v3。條件固定（Codespaces、CPU、3B 模型、`TOP_K=4`），一次只改一個開關。
- 結果：**只有分類取回（`SPLIT_RETRIEVAL`）值得預設開啟**——取回內容中文件的比例 95% → 25%，程式碼檔命中 1/9 → 6/9，檢索時間仍是 0.07～0.21 秒。其餘預設都維持關閉：混合檢索在分類取回之上沒有額外效果；metadata 與 prompt v2 沒有改善；常見的 0.70 相似度門檻會丟掉 93% 的正確片段；rerank 要付 +4.8 秒與約 +10 秒首字延遲；prompt v3 的可回答題誤拒率是 8/9。
- 最大的收穫不是哪個技巧有效，而是：**單看 B 組（混合檢索）會誤以為它很有效，直到補跑 D 組對照才發現分類取回早就做到了。**
- 正確性評分（AI 判讀，最不確定的 5 題由人複核）的結果一致：分類取回讓答對的分數從 11 變成 17（/30）；rerank 的 I 組同樣是 17 分，卻每次查詢多約 10 秒；第 2 題 8 組都是 0 分，因為正確的檔案從來沒被取回。**檢索變好，不一定等於答得更好。**
- **這些都只在 20 個檔案的範例專案、每組只跑一次、3B 的 CPU 模型上量過，且大部分正確性分數沒有人確認。**

## 1. 起點：回答是錯的，因為取回的 4 段全是文件

範例專案裡有一個常見的新人問題：「玩家受傷後的無敵時間在哪裡設定？」好的回答應該指出 `src/config/gameConfig.ts` 的 `INVINCIBLE_MS = 1500`，以及 `src/entities/Player.ts` 裡使用它的地方。

在 Codespaces 上（`qwen2.5-coder:3b`、`TOP_K=4`），我從瀏覽器問了這題。串流很順（首字延遲 30.4 秒、總耗時 43.8 秒），但取回的 4 個引用是：

```text
引用的檔案：[1] README.md:26-32 [2] docs/gameplay.md:10-14 [3] docs/architecture.md:1-9 [4] docs/architecture.md:11-20
玩家受傷後的無敵時間是在 `docs/gameplay.md` 文件的第 10 行到第 14 行設定的。…
```

[截圖：介面顯示 4 個引用都是 .md，回答說無敵時間定義在 docs/gameplay.md]

這個回答有兩個問題，而且是兩種不同的問題：

1. **檢索問題**：4 個片段全是文件，定義常數的程式碼一個都沒取回。模型只能引用文件，於是說值「定義在 `docs/gameplay.md`」。
2. **生成問題**：回答混進了簡體字（具体来说、代码、无、时间、定义）。

（注意這個回答同時含有 `INVINCIBLE_MS` 這個字，但指向的是錯的檔案。關鍵字有命中不等於答對，這正是下一節要講的。）

我的第一個猜測是：中文問題跟中文文件在 embedding 空間比較近，`TOP_K=4` 的 4 個名額被文件占滿。**這是猜測，當時沒有驗證**——所以接下來要做的不是調參數，而是先能量。

## 2. 先做評估工具，再改東西

沒有數字之前改檢索，只會得到「這次問的那一題看起來好了」。我先寫 `scripts/evaluate.py`（ADR 0012），再做任何改動。

### 指標設計

評估腳本透過 `/query/stream`（跟介面同一條路徑）問每一題，每題記錄：

| 指標 | 怎麼算 | 為什麼需要 |
| --- | --- | --- |
| 定義檔命中（定位設定題） | 取回的片段中，有沒有 `definition_files` 裡的**程式碼**檔 | 問「X 在哪裡設定」，只取回提到 X 的文件不算 |
| 程式碼檔命中／文件檔命中 | 預期檔案是否被取回，依副檔名（`.md` 算文件）分開 | 直接看出文件把程式碼擠掉 |
| 取回片段中文件的比例 | 取回片段中 `.md` 的比例 | 不依賴預期清單的偏差指標 |
| 回答引用預期檔案 | 回答中的 `[n]` 對應到來源 | 模型有沒有用到對的片段 |
| 關鍵字命中率 | 不分大小寫的子字串比對，任一替代寫法都算 | 粗略確認關鍵事實有出現 |
| 簡體字 | 200 個只存在於簡體的字，在本 repo 繁體文件上零誤判 | 小模型的語言漂移 |
| 拒答（陷阱題） | 出現拒答用語，且沒有禁用關鍵字（`WebSocket`…） | 抗幻覺 |
| 首字延遲、總耗時 | 用戶端從送出請求量起 | 使用者感受到的速度 |

另外，**人工判定正確性**（每題 0～2 分）是一個空白欄位，由人填完再用 `--apply-manual` 寫回。自動數字從不叫「正確率」。

### 這些指標的限制（ADR 0012 寫在決策裡）

- **關鍵字命中不等於答對。** 第 1 節那個錯誤回答，就同時含有 `INVINCIBLE_MS` 與 1500，卻說定義在錯的檔案。
- **檔案命中率量的是取回了什麼，不是用了什麼。** 模型可以忽略取回的檔案，或引用錯的。
- **預期清單是我自己列的。** 另一個片段也可能答得出來，沒命中是「該去看一眼」，不是「失敗」。
- **拒答偵測是字串比對。** 這一點後面會真的出事（第 8 節）。
- 10 題是很小的樣本，差一題就是雜訊。

這就是為什麼本文反覆強調：現在的數字是**篩選訊號**，不是答案品質。

### 一個早期的教訓：同一題問兩次

同一題連問兩次，首字延遲從 30.4 秒變成 0.8 秒，因為 Ollama 重用了快取的提示詞。所以腳本一律問 10 個**不同**的問題、先送一題不計分的暖機問題，也絕不重複同一題。後面第 4.1 節我還會再被快取騙一次。

## 3. 實驗設計

### 固定的條件

| 項目 | 值 |
| --- | --- |
| 環境 | GitHub Codespaces，4 核心／16GB，只有 CPU |
| 模型 | `qwen2.5-coder:3b`、`nomic-embed-text` |
| `TOP_K`／`LLM_NUM_CTX` | 4／8192 |
| 範例專案 | 20 個檔案、67 個片段 |
| 暖機 | 開啟（每組一題不計分） |
| 每組跑幾次 | **一次** |

### 一次只改一個開關

每個技巧都是 `.env` 開關，預設全關（ADR 0013）。每組都用 shell 變數覆寫、跑完用 `/health` 確認開關與預期一致，再執行評估。每次執行的失敗數都是 0（devlog 2026-11-03）。

### 兩個題庫

- **主題庫**（`questions.yaml`，10 題）：用團隊平常的問法，大多**沒有寫出識別字**。第 1 題不會說 `INVINCIBLE_MS`。類型：定位設定 3、解釋邏輯 3、跨檔案流程 3、陷阱題 1。
- **識別字題庫**（`questions-identifiers.yaml`，5 題）：問題裡寫出識別字，例如「`INVINCIBLE_MS` 在哪裡定義？」。

分兩個題庫是因為我預期關鍵字類的技巧只在有識別字的問題上有用。事後看這個預期是對的，只是原因比我想的更乾淨（第 4.1 節）。

### 組別

| 組 | 開關 | 想回答的問題 |
| --- | --- | --- |
| A 基準線 | 全部關閉 | 參考數字 |
| B 混合檢索 | `HYBRID_SEARCH` | 關鍵字加識別字比對能不能把定義的程式碼帶進來？ |
| C 分類取回 | `SPLIT_RETRIEVAL`、`DOC_TOP_K=1` | 限制文件名額能不能不讓文件擠掉程式碼？ |
| D 混合 + 分類 | B + C | 兩者會不會相加？ |
| E metadata 單獨 | `CHUNK_METADATA` | **沒有執行**（選用，併入 F） |
| F 全開 | B + C + `CHUNK_METADATA` + `PROMPT_VARIANT=v2` | 整包 |
| G 門檻 | `SCORE_THRESHOLD` | **校準後不採用，沒有執行**（第 4.4 節） |
| H rerank | `RERANK`，10 → 4 | cross-encoder 能不能把定義的程式碼排進前 4？ |
| I 混合 + 分類 + rerank | B + C + `RERANK` | rerank 加在 D 上有什麼用？ |
| J D + prompt v3 | `PROMPT_VARIANT=v3` | 明確的「找不到」規則能不能讓 3B 模型拒答不存在的功能？ |

10 個組別編號，實際執行的是 8 組（A、B、C、D、F、H、I、J）；G 只做了校準，E 沒做。D 原本也被我跳過，後來補跑，而這一補跑改變了我對 B 與 I 的結論。

## 4. 逐一實驗

每一段都照「預期 → 結果 → 為什麼」。結果是自動指標；正確性（AI 判讀）放在全貌表與 4.7 節。

### 先看全貌

[圖表：A → J 各組的「定義檔命中（主要題庫）」「程式碼檔命中」「文件比例」長條圖]

| 組 | 定義檔命中，主要 | 定義檔命中，識別字 | 程式碼檔命中，主要 | 取回片段中文件比例，主要 | 正確性（AI），主要／識別字 |
| --- | --- | --- | --- | --- | --- |
| A 基準線 | 0/3 | 1/3 | 1/9 | 95% | 5 / 6 |
| B + 混合檢索 | 0/3 | 3/3 | 3/9 | 88% | 9 / 7 |
| C + 分類取回 | 1/3 | 3/3 | 6/9 | 25% | 7 / 10 |
| D 混合 + 分類 | 0/3 | 3/3 | 6/9 | 25% | 7 / 9 |
| F 全開（+ metadata、v2） | 0/3 | 3/3 | 5/9 | 25% | 6 / 10 |
| H + rerank | 0/3 | 2/3 | 2/9 | 85% | 6 / 8 |
| I D + rerank | 3/3 | 3/3 | 7/9 | 23% | 8 / 9 |
| J D + prompt v3 | 0/3 | 3/3 | 6/9 | 25% | 3 / 5 |

### 4.1 混合檢索（B）

**預期**：問題裡寫了 `INVINCIBLE_MS`，向量檢索卻被中文文件吸走；加上 BM25 與「識別字定義比對」（以 RRF 合併），應該能把宣告它的 `gameConfig.ts` 帶進來。

**結果（單看 B）**：識別字題庫的定義檔命中從 **1/3 變成 3/3（33% → 100%）**，文件比例 60% → 30%，檢索時間只有幾毫秒。看起來是大贏。

主題庫則幾乎沒動：定義檔命中 0/3 → 0/3，程式碼檔命中 1/9 → 3/9，文件比例 95% → 88%。

**為什麼主題庫沒動**：這是實作時就看到的現象。我最初的 BM25 對中文用字元 bigram，拿「玩家受傷後的無敵時間在哪裡設定？INVINCIBLE_MS 是多久？」去查，排名是：

```text
45.5  README.md            Starlight Courier（範例專案） > 可以試著問的問題
19.7  docs/gameplay.md     玩法規則 > 生命與受傷
 9.9  src/entities/Player.ts
 8.7  src/config/gameConfig.ts
```

文件是中文、程式碼不是，問題的每個中文 bigram（無敵、敵時、時間、設定…）都只比對得到文件，蓋過了唯一一個精確的識別字。**關鍵字通道在放大我想修的問題。** 修正是 BM25 只索引 ASCII 的單字、識別字與數字，中文的語意留給向量通道。代價就是：**主題庫的問題沒有識別字，BM25 無從比對。** B 組主題庫 10 題中有 7 題取回的片段跟 A 組完全一樣。

**一個延遲的陷阱**：B 的首字延遲平均是 6.7 秒，A 是 13.0 秒，看起來快了一倍。但檢索時間在每一組都只有 0.07～0.21 秒，混合檢索不可能省這麼多。逐題看，第 2、4、9 題首字只要約 0.2 秒——這三題取回的片段跟 A 完全相同，提示詞一樣，是 Ollama 重用了快取。片段有變的第 5、8 題沒有比較快（11.7 → 13.9 秒、16.2 → 15.0 秒）。**所以 B 的延遲不能解讀成改善。**

**單看 B 的結論（後來被修正）**：混合檢索很有效，識別字題從 1/3 到 3/3。

**D 組對照之後**：C（只有分類取回）在識別字題庫**也是 3/3**。也就是說，那個 33% → 100% 的進步，不需要 BM25 也拿得到。更糟的是主題庫：

- 第 1、9 題：D 取回的片段跟 C 完全一樣（只有向量通道，中文問題給 BM25 的東西是零）。
- 第 8 題（`InputManager.ts`）：C 有取回（向量通道）。D 裡，RRF 把「向量和關鍵字都找到」的候選（`Player.ts`、`Hud.tsx`、`Game.ts`）排在它前面，**混合檢索把它擠掉了**。定義檔命中：C 1/3，D 0/3。

**結論**：混合檢索在分類取回之上沒有額外效果，在主題庫上還擠掉過一題；它只對「問題裡寫出識別字」且**沒有**分類取回的情況有用，成本是幾毫秒。維持選用、預設關閉。

這一節如果我只跑了 A、B 就停手，我會把混合檢索寫進預設值。

### 4.2 分類取回（C）

**預期**：文件跟中文問題在 embedding 空間很近，只要限制取回名額中最多 `DOC_TOP_K=1` 個文件，剩下留給程式碼，程式碼檔就會進來。

**結果**（主題庫，僅自動指標）：

| 指標 | A | C |
| --- | --- | --- |
| 取回片段中文件比例 | 95% | **25%**（剛好是 `DOC_TOP_K=1` 的上限） |
| 程式碼檔命中 | 1/9 | **6/9** |
| 定義檔命中，主要 | 0/3 | 1/3（第 8 題） |
| 定義檔命中，識別字 | 1/3 | **3/3** |
| 檢索時間 | 0.07～0.21 秒（每一組都是） | 同左 |

**為什麼有效**：它不改變「哪個片段比較像」，只改變**名額怎麼分**。文件跟問題用同一種語言，永遠贏過英文程式碼；與其想辦法讓程式碼更像，不如保證程式碼有座位。這也解釋了它為什麼幾乎沒有成本：只是在 30 個候選上做分配，不用多一次模型呼叫。

**它沒解決的事**：
- 第 1 題（`gameConfig.ts`、無敵時間）在 C 裡**仍然取不到**。定義檔命中主題庫只有 1/3。
- 簡體字的回答變多：C 有 3 個，A 只有 1 個。我的假設（**未驗證**）：提示詞裡程式碼變多，3B 模型更容易漂移到簡體。
- 首字延遲變長（15.9 秒 vs A 的 13.0 秒），因為取回的程式碼片段比文件長（例如第 3 題 146 行 → 47 秒）。延遲比較因為快取效應不可靠（見 4.1），這裡只能說「看起來」。

**我檢查過的風險**：文件名額被限制到 1，**重點本來就在文件的題目**（第 2、3、6 題）可能變差。沒有：基準線是 0／2／2，C 也是 0／2／2（AI 判讀，4.7 節）。

**結論**：整個實驗裡「收益對成本」最好的一個。**唯一預設開啟的開關**（`.env.codespaces`，ADR 0018）。第 2、3、6 題沒有退步。

### 4.3 Chunk metadata 與 prompt v2（F）

**預期**：把「Defines: … INVINCIBLE_MS」這類標頭放進 embedding 文字，應該能讓「無敵」比對到 `INVINCIBLE`；prompt v2（固定繁體、第一段先給檔案與行號）應該壓住簡體字。

**結果**（F = B + C + metadata + v2，與 C 比）：

| 指標 | C | F |
| --- | --- | --- |
| 定義檔命中，主要 | 1/3 | **0/3** |
| 程式碼檔命中，主要 | 6/9 | 5/9 |
| 回答引用預期檔案（`[n]`），主要 | 1/9 | 4/9 |
| 簡體字的回答，主要 | 3 | 2 |
| 平均回答 token 數 | 109 | 241 |
| 總耗時平均，主要 | 25.7 秒 | 42.8 秒 |

**為什麼沒用**：
- 第 1 題仍取不到 `gameConfig.ts`——標頭並沒有讓「無敵」對上 `INVINCIBLE`（`nomic-embed-text` 對這種中英對應沒有幫助）。
- F 還丟了 C 在第 8 題的命中：metadata 改變了所有程式碼片段的 embedding。
- v2 讓回答更長、開頭先列 `[n] 路徑:行號`，所以「引用預期檔案」從 1/9 變成 4/9。**這是格式改變，不是檢索改善**，回答是否更正確要等人工評分。
- 簡體字還是有 2 個（`体`、`冲`）。只靠提示詞，3B 模型壓不住。

**結論**：沒有改善，維持關閉。它還有隱性成本：`CHUNK_METADATA` 一改就要全量重建索引（18.8～20.7 秒）。

### 4.4 相似度門檻（G）：客服 RAG 的 0.70，在這裡行不通

**預期**：陷阱題（「線上多人模式怎麼同步玩家位置？」，範例專案根本沒有這個功能）取回的片段分數應該偏低；設一個門檻，低於它就不呼叫 LLM、直接回「找不到」。客服類 RAG 常見的做法是 0.70。

**做法**：不憑感覺選值。`calibrate_threshold.py` 從 A、C 的報告（主題庫 + 識別字題庫）收集所有取回片段的 cosine 分數，分成「預期檔案的片段」「其他檔案的片段」「陷阱題的片段」，再列出每個候選門檻會丟掉多少正確片段。

**結果：分布幾乎重疊**

| 片段 | 數量 | 中位數 | 範圍 |
| --- | --- | --- | --- |
| 預期檔案（正確） | 27 | **0.616** | 0.487–0.745 |
| 其他檔案（不相關） | 63 | **0.604** | 0.466–0.759 |
| 陷阱題 | 7 | 0.542 | 0.478–0.570 |

| 門檻 | 丟掉的正確片段 | 擋掉的其他片段 | 失去所有預期片段的題數 | 陷阱題拒答 |
| --- | --- | --- | --- | --- |
| ≤ 0.45 | 0/27 | 0/70 | 0 | 0/1 |
| 0.50 | 2/27（7%） | 10/70（14%） | 0 | 0/1 |
| 0.55 | 4/27（15%） | 18/70（26%） | 2 | 0/1 |
| 0.60 | 13/27（48%） | 36/70（51%） | 6 | 1/1 |
| **0.70** | **25/27（93%）** | 69/70（99%） | **10** | 1/1 |

（資料來自 A、C 兩組的主題庫與識別字題庫共 15 題；「擋掉的其他片段」的分母是 70，因為把陷阱題的 7 個片段也算進「非預期」。）

**為什麼**：正確片段的中位數 0.616，不相關片段的中位數 0.604，差 0.012。cosine 分數**沒有告訴你這個片段相不相關**。0.70 會丟掉 27 個正確片段中的 25 個（93%），並且讓 15 題中的 10 題失去所有預期片段。唯一拒答陷阱題的 0.60，已經讓 6 個真實問題一片正確片段都沒有。≤ 0.45 的值安全，但什麼都擋不到。

校準腳本的結論是「**不建議任何數值**」，所以 G 組根本沒有執行，`SCORE_THRESHOLD` 維持空白。

一個延伸的限制：metadata 索引（F）也無法校準，因為 F 的報告是 `vector_score` 還不存在時寫的，沒有 cosine 分數。而且門檻值跟 embedding 模型綁在一起，換模型就得重新校準。

[圖表：預期片段 vs 不相關片段的 cosine 分布（箱型圖），標出 0.70]

**結論**：不採用。要拒答陷阱題，需要別的訊號。

### 4.5 Rerank（H、I）

**預期**：cross-encoder 看的是（問題, 片段）一對，比 embedding 的餘弦更準，應該能把定義的程式碼排進前 4。

**單獨開（H）**：沒用。

| 指標 | A | H |
| --- | --- | --- |
| 定義檔命中，主要／識別字 | 0/3／1/3 | 0/3／2/3 |
| 程式碼檔命中，主要 | 1/9 | 2/9 |
| 文件比例，主要 | 95% | 85% |
| rerank 耗時（平均） | — | 2.9 秒（主要）／4.4 秒（識別字） |
| 首字延遲平均，主要 | 13.0 秒 | 21.2 秒 |

**為什麼**：rerank 只能對**向量取回的 10 個候選**重新排序，而主題庫的 10 個候選幾乎全是 Markdown，裡面沒有程式碼可選。而且通用 reranker 偏愛文件：Markdown 片段得分 0.8～0.99，程式碼片段大多低於 0.1。改變「**哪些**候選存在」的 B、C 在識別字題庫是 3/3，H 只有 2/3。

**搭配分類取回與混合檢索（I = D + rerank）**：

| 指標 | D | I |
| --- | --- | --- |
| 定義檔命中，主要 | **0/3** | **3/3** |
| 程式碼檔命中，主要 | 6/9 | 7/9 |
| 簡體字的回答，主要／識別字 | 4／2 | 0／0 |
| rerank 耗時（主要） | — | 4.8 秒（2.4–6.7） |
| 首字延遲平均，主要 | 17.2 秒 | 26.8 秒（**+9.6 秒**） |

主題庫的定義檔終於全中：第 1 題的 `gameConfig.ts` 排第一，第 8 題 `InputManager.ts`，第 9 題 `GameState.ts`。第 1 題的回答這次指向 `src/config/gameConfig.ts`、`INVINCIBLE_MS`、1500 ms（只做了關鍵字檢查，正確性待評）。

**但是**：
- **分數極小。** 第 1 題被推上來的 `gameConfig.ts` rerank 分數是 0.0027，下一個程式碼片段是 0.0003；第 8 題是 0.0738，其他程式碼片段 0.0003～0.03。排序很脆弱，這個增益只是 3 題、各跑一次。
- **成本。** rerank 每次查詢 4.8 秒（程式碼片段比文件長，所以比 H 的 2.9 秒多）；首字延遲 D → I 多約 10 秒（17.2 → 26.8 秒）；backend 映像檔 616 MB → 2.14 GB（+1.5 GB）。reranker 的微基準測試：`bge-reranker-base` 10 組 3.73 秒，對照 `bge-reranker-v2-m3` 11.97 秒（4 vCPU 雲端容器，不是 Codespace）。
- **識別字題庫上 rerank 什麼都沒加**：C、D、I 都是 3/3，反而「引用預期檔案」從 4/5 降到 2/5。
- **rerank 分數也分不出陷阱題。** I 組中第 10 題最高分 0.33，但真實問題第 9 題最高分只有 0.0165。
- 還有一個沒量的對照：**C + rerank（沒有混合檢索）**。D 已經顯示混合檢索在主題庫沒用，這個組合可能用同樣的 rerank 成本拿到 I 的結果。選 D 或 I 當預設之前值得跑一次。

**我一度把功勞算錯**：在還沒有 D 組之前，我把第 8 題的命中歸功於混合檢索。D 組補跑之後才看到，第 8 題在 C（純向量）本來就有，是混合檢索擠掉它，rerank 又把它救回來。這段對照也是第 4.1 節的來源。

**結論**：預設維持關閉。是目前主題庫檢索最好的組合，但要付 4.8 秒 rerank、約 10 秒首字延遲、1.5 GB 映像檔，而收益建立在 0.003～0.07 的分數上。

### 4.6 防幻覺 prompt v3（J）：把陷阱題拒答，也把真問題一起拒答

**預期**：3B 模型對陷阱題（A～I 沒有任何一組拒答第 10 題）會編造答案。在提示詞裡加一條明確規則：「如果沒有任何片段直接提到這個主題，只回答固定的一句『找不到』」，應該能拒答陷阱題。

**做法**：J = D + prompt v3。我另外建了範圍外題庫（8 題：陷阱題 21～25 共 5 題、對照題 26～28 共 3 題，後者是專案**有**、但容易被誤認為沒有的功能，例如存檔、音效、視窗失去焦點），並先用 D（prompt v1）當對照跑一次。J 在全部 23 題取回的片段跟 D **完全相同**，所以所有差異都來自提示詞。

**結果**：

| 指標 | D（v1） | J（v3） |
| --- | --- | --- |
| 陷阱題拒答，範圍外 21～25 | 2/5（關鍵字篩選，依 ADR 0019 重新計分；原本是 1/5） | **5/5** |
| 第 10 題拒答 | 否 | **是** |
| 誤拒率，對照題 26～28 | 0/3 | **3/3** |
| 誤拒率，主題庫（9 題可回答） | 0/9 | **8/9** |
| 誤拒率，識別字題庫 | 0/5 | **2/5** |
| 回答只有那句固定句子 | 0/23 | **19/23** |
| 關鍵字命中率，主要／識別字 | 28%／83% | 18%／48% |

**為什麼**：J 的 23 個回答裡有 19 個一字不差是「在索引的專案中找不到相關內容。」（11 個 token）。v3 沒有分辨真問題與陷阱題，只是把模型推向最短最安全的輸出。被拒答的真問題包括**預期檔案已經全部取回**的（主題庫第 5 題 2/2；識別字第 11、13 題的識別字 `INVINCIBLE_MS`、`DASH_COOLDOWN_MS` 一字不差出現在取回片段裡）。我的假設（**未驗證**）：「如果沒有片段『直接』提到這個主題」是一個判斷，3B 模型做不穩，而這條提醒又是它在 `## Answer` 前讀到的最後一句話。

另一個細節：首字延遲沒降（20.3 秒 vs 17.2 秒，但這個差異有快取雜訊），因為模型還是得先讀完整個提示詞才寫出拒答；總耗時降了約 3 秒，只因為答案短。

**結論**：不採用。實驗計畫在動手之前就寫好了決策規則：**誤拒率必須在每個題庫都維持 0**，因為「找不到」會把真實存在的程式碼藏起來，一次誤拒比少拒答一題陷阱題更糟。v3 在 14B（Mac）上還沒試過，失敗可能只出在 3B。

### 4.7 檢索變好，就會答得更好嗎？正確性評分

**怎麼評分**：全部 136 個回答（8 組 × 15 題，加上 16 個範圍外題目的回答）對照範例專案原始碼，評 0（錯誤或編造）、1（部分正確）、2（關鍵事實全對）。每題的回答先去掉組別名稱、打亂順序再評，確保各組標準一致。**評分者是 AI（Claude），不是人。** 最不確定的 5 題由人複核，結論沒有改變；其餘分數沒有人確認。

| 組 | 主要（/20） | 識別字（/10） | 合計（/30） |
| --- | --- | --- | --- |
| A 基準線 | 5 | 6 | 11 |
| B + 混合檢索 | 9 ¹ | 7 | 16 |
| **C + 分類取回** | **7** | **10** | **17** |
| D 混合 + 分類 | 7 | 9 | 16 |
| F 全開（+ metadata、v2） | 6 | 10 | 16 |
| H + rerank | 6 | 8 | 14 |
| **I D + rerank** | **8** | 9 | **17** |
| J D + prompt v3 | 3 | 5 | 8 |

¹ B 在主要題庫的第一名，建立在三題給 1 分、也可能是 0 分的回答上；改成 0 分就是 6，低於 C。

分數說了三件事：

1. **C = I = 17 分（/30），但 I 每次查詢多約 10 秒。** I 是在 D 之上加 rerank（+4.8 秒），首字延遲 26.8 秒對 D 的 17.2 秒，還要一個 2.15 GB 的映像檔。它比 C 多拿第 1、9 題，卻少了第 3、8 題。付出這些代價卻沒有多答對題目，不划算，所以 rerank 維持關閉。
2. **第 2 題（連擊倍率）8 組都是 0 分，這是檢索缺口，不是開關造成的。** 沒有任何一組的前 4 名有 `ScoreSystem.ts` 或 `gameConfig.ts`，而且中文問題沒有識別字（`COMBO_STEP`）可以讓關鍵字管道抓到。眼前沒有相關內容時，3B 模型就編造一個 `Player.ts` 的連擊邏輯和錯誤的數值。本文的開關都救不了它；下一步是試中文 → 識別字的對照表。
3. **檢索變好，不等於答得更好。** I 的檢索最好（定義檔 3/3、程式碼 7/9、關鍵字命中 45%），主要題庫只比 C 多 1 分，識別字題庫少 1 分。C、D 的第 7、9 題即使取回了預期的程式碼檔仍是 0 分：3B 模型從錯的檔案（`Player.ts`、`Hud`、`UiStore.score`）作答，而不是讀取回的片段。檢索指標告訴你模型看到了什麼，不是它有沒有讀懂。

我一直在等的檢查結果：分類取回沒有讓重點在文件的題目變差。第 2／3／6 題在基準線是 0／2／2，在 C 也是 0／2／2。

**但書**：每組只跑一次，3B 模型每次的措辭都不同（C 與 D 的 10 題主要題庫回答文字全都不同，總分卻相同）。1 分是雜訊；只有大差距（分類取回對基準線、v3 墊底）可以放心解讀。

## 5. 最終預設值

devlog 2026-11-03 的建議，經正確性評分確認後，已**套用在 `.env.codespaces`**（[ADR 0018](../../decisions/0018-codespaces-default-retrieval-settings.md)）。`.env.example`（Mac）沒有改：

| 開關 | 建議（Codespaces、3B、CPU、`TOP_K=4`） | 理由 |
| --- | --- | --- |
| `SPLIT_RETRIEVAL=true`、`DOC_TOP_K=1` | **開啟**（已套用；第 2、3、6 題沒有退步） | 毫秒級成本換最大收益：程式碼檔 1/9 → 6/9、文件比例 95% → 25%、識別字題庫定義檔 1/3 → 3/3 |
| `HYBRID_SEARCH` | 維持關閉（選用） | 分類取回之上沒有額外效果；主題庫上擠掉過第 8 題（D 0/3 vs C 1/3）；只花毫秒 |
| `RERANK` | 維持關閉 | I 的檢索最好（定義檔 3/3），但 +4.8 秒、約 +10 秒首字延遲、+1.5 GB 映像檔，增益建立在 0.003～0.07 的分數上；C + rerank 尚未測 |
| `CHUNK_METADATA` | 維持關閉 | F 沒有增益，還丟了 C 的第 8 題命中；改它要全量重建索引 |
| `SCORE_THRESHOLD` | 留空 | 沒有可校準的值（正確 0.616 vs 不相關 0.604） |
| `PROMPT_VARIANT` | 維持 `v1` | v2 沒有檢索增益、簡體字仍有 2 個；v3 的誤拒率主題庫 8/9 |
| `QUERY_GLOSSARY` | 維持關閉（已實作，尚未實驗） | 只做過離線檢查（3/19 → 16/19，上限）；端到端的 K 組 {待填}；需搭配 `HYBRID_SEARCH`（ADR 0020） |

實驗計畫自己的決策規則是：「開關要改成預設開啟，必須證明**定義檔命中或人工正確性**變好，而且**任何題型的人工正確性都沒有變差**，並為預設值的改變新增一份 ADR。」分類取回符合這條規則（正確性 11 → 17／30，第 2、3、6 題沒有變差）；預設值的改變，連同其他開關維持關閉的理由與證據的限制，都記錄在 ADR 0018。

Mac（14B、`TOP_K=8`）的 `.env.example` 沒有改，要等 `./scripts/benchmark-mac.sh` 實測：`TOP_K=8` 時的 `DOC_TOP_K` 沒測過。

## 6. 學到的事

1. **對照組比單組結果重要。** 只有 A、B 的話，我會宣布混合檢索有效，識別字題從 1/3 到 3/3。補了 C 才知道 C 單獨就做得到；補了 D 才知道混合檢索在主題庫還會擠掉一題。同樣的，I 的功勞一度被我算給混合檢索，是 D 組把它修正成 rerank。**每一個「有效」都要問：把它拿掉，剩下的哪個開關其實已經做到了？**
2. **拒答率與誤拒率要一起看。** v3 的拒答率 5/5 很漂亮，同一張表另一欄的誤拒率是 8/9。只報前者，它就是一個成功的實驗。
3. **通用建議要用自己的資料驗證。** 0.70 在客服 RAG 常見，在這份資料上會丟掉 93% 的正確片段，因為正確與不相關片段的 cosine 分布重疊；rerank 的通用模型給文件 0.8～0.99、給程式碼大多低於 0.1。這些建議本身沒錯，只是前提（文件跟問題同語言、分數能分辨相關性）在「中文問題 + 英文程式碼」的 codebase 不成立。
4. **評估腳本本身也會有漏洞。**
   - 陷阱題的拒答關鍵字原本列了「無法」，沒列簡體的「无法」。範圍外第 22 題的回答「我无法提供…」是一個用簡體字寫的拒答，被算成「沒拒答」。ADR 0019 改成一份繁簡對照清單，並重新計分舊報告。
   - 第 23 題（說「透過 `syncUi`」同步到雲端）與第 25 題（說手把對應到鍵盤處理函式）是**編造的回答**，卻通過「沒拒答、沒有禁用關鍵字」的檢查。人工讀過 D 的回答，實際拒答 2/5；修正前關鍵字篩選只算出 1/5，修正後是 2/5。這類「用真實名稱編造行為」的回答，ADR 0019 新增的編造檢查（檢查檔案與符號是否存在）仍然抓不到。
   - 另一邊，第 28 題的「没有直接处理…的逻辑」是錯誤回答，但單獨的「没有」刻意不算拒答字句，所以也不算誤拒。
   - 這些不影響 J 的數字（它的拒答是一字不差的固定句），但影響 D 這個對照組。
5. **延遲數字很容易騙人。** B 組「快一倍」是提示詞快取；同一題問兩次差 40 倍。比較各組延遲要小心，而不是把它當成技巧的功勞。
6. **後端程式碼合併後要重建映像檔。** 跑 J 時後端起不來（`PROMPT_VARIANT must be one of ['v1', 'v2'], got 'v3'`），因為映像檔是為 H、I 建的，早於 v3 的程式碼。這次會失敗得很大聲；不會在啟動時失敗的改動，就不會被發現。
7. **檢索變好，不等於答得更好。** Rerank 給了整個實驗最好的檢索，答對的分數卻和成本最低的開關一樣是 17 分。檢索指標量的是模型看到了什麼，不是它拿來做了什麼；旁邊要有一欄正確性，而且要從一開始就有。

---

## 7. 限制

- **只有 20 個檔案、67 個片段**的範例專案。真實專案 50～300 個檔案，候選池大小、BM25 行為與 cosine 分布都可能不同。
- **每組只跑一次。** 差一題就是雜訊，沒有重複執行來估計變異。
- **3B 的 CPU 模型**（`qwen2.5-coder:3b`、`TOP_K=4`、4 核心）。正式環境是 Mac M2 上的 14B、`TOP_K=8`；v3 在 14B 上可能有不同結果。這個差距沒有量過。
- **正確性由 AI 判讀。** 回答由 Claude 評分；只有最不確定的 5 題由人複核（結論沒有改變）。主要機制正確、漏掉次要事實時，評得偏寬。關鍵字命中率仍然不是正確率。
- **兩個題庫都由我設計**，預期檔案清單也是我列的。
- 簡體字的判斷用保守的 200 字清單，只抓得到明顯漂移。
- 延遲受提示詞快取與執行順序影響，沒有重複量測。
