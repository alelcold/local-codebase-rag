# Devlog 2026-11-02 — Streaming answers and a dev container for Codespaces

> English first; 繁體中文版本在下方.
> Privacy: only the sample project (`examples/sample-game-frontend/`) was indexed and queried.

## What I did

- Added `POST /query/stream` (Server-Sent Events): sources first, then the answer token by token, heartbeats while the model is silent, a `done` event with timing. The UI uses it; `/query` is unchanged. ADR [0010](../decisions/0010-streaming-responses.md).
- nginx: a separate location for the stream with buffering and gzip off.
- The smoke test (also in CI) runs a streaming query and checks event order and that events arrive spread out in time.
- `.devcontainer/` so a codespace starts Ollama, the models and the stack by itself, on every start; `docker-compose.codespaces.yml`, `.env.codespaces`, `scripts/doctor.sh`. ADR [0011](../decisions/0011-devcontainer-for-codespaces.md).

## Problems

### Problem 1 (#9 in the test log): The browser got 504 after about 100 s, `curl` succeeded in 54.7 s

- **Problem**: In Codespaces, a query sent with `curl` inside the codespace through nginx finished in **54.7 s**. The same query from the browser, through the Codespaces port forwarding URL, failed with **504** after about **100 s**.
- **Error message**:

  ```text
  {待補：介面顯示的錯誤訊息（504）}
  ```

- **Cause**: The port forwarder in front of nginx has its own limit, which the 300 s settings for nginx and the backend (ADR 0009) cannot change. `/query` sends nothing until the whole answer is ready, so the connection carries no data for a minute or more. Why the browser request took longer than `curl` (cold model, different `top_k`, or waiting in line behind another request) was not established. {待補}
- **Fix**: Stream the answer (ADR 0010). The backend sends a first event immediately and a heartbeat at least every `STREAM_HEARTBEAT_SECONDS` (10 s), then the sources, then the tokens, so the connection is never idle. {待填：在 Codespaces 透過轉發網址實測串流查詢的結果}

### Problem 2: A local check showed `proxy_buffering on` alone did not hold the stream back, gzip did

- **Problem**: To make sure the smoke test can detect a buffering proxy, the stream was sent through an nginx with `proxy_buffering on` (and `X-Accel-Buffering` ignored). The events still arrived one by one, so the check would never fail.
- **Error message**: none; the test passed when it should have failed.
- **Cause**: nginx 1.29 passes buffered data on as soon as it can when the client reads fast enough. The setting that really held the stream back was **gzip**: with `gzip on` for `text/event-stream`, all 13 tokens of a 4-second answer arrived in the same instant at the end. The smoke test's `curl` did not send `Accept-Encoding: gzip`, so nginx never compressed and the problem stayed hidden. Browsers always send it.
- **Fix**: The stream location has `gzip off` as well as `proxy_buffering off`. The smoke test uses `curl --compressed`, stamps each line with its arrival time, and with `STREAM_STRICT=1` (CI) fails when all events arrive within 0.1 s although the backend streamed for over a second. Checked against the broken config: `✗ All events arrived within 0.00s although the backend streamed for 4.321s.`

## Concepts learned

- **Streaming keeps proxies happy**: a response that sends bytes regularly is not cut by idle limits, and the user sees progress. See [knowledge checklist §14](../learning/knowledge-checklist.md#14-server-sent-events-and-streaming-responses).
- **Buffering and compression both delay streams**, and a test client has to behave like a browser to notice. See [§15](../learning/knowledge-checklist.md#15-reverse-proxy-buffering).
- **`postStartCommand` runs on every start, `postCreateCommand` once**: servers belong in the first. See [§16](../learning/knowledge-checklist.md#16-dev-containers-and-codespaces).

# 開發日誌 2026-11-02 — 串流回答與 Codespaces 的 dev container

> 隱私：只索引並查詢範例專案（`examples/sample-game-frontend/`）。

## 做了什麼

- 新增 `POST /query/stream`（Server-Sent Events）：先送引用片段，再逐 token 送出回答，模型沉默時送 heartbeat，最後送出含耗時統計的 `done` 事件。介面改用它；`/query` 不變。ADR [0010](../decisions/0010-streaming-responses.md)。
- nginx：為串流另設一個 location，關閉緩衝與 gzip。
- 冒煙測試（CI 也會跑）新增串流查詢，檢查事件順序，以及事件是否分散在不同時間到達。
- 新增 `.devcontainer/`，codespace 每次啟動都會自動啟動 Ollama、準備模型並啟動服務；另有 `docker-compose.codespaces.yml`、`.env.codespaces`、`scripts/doctor.sh`。ADR [0011](../decisions/0011-devcontainer-for-codespaces.md)。

## 遇到的問題

### 問題 1（測試紀錄 #9）：瀏覽器約 100 秒後收到 504，`curl` 卻在 54.7 秒成功

- **問題**：在 Codespaces 裡，從 codespace 內用 `curl` 經 nginx 查詢，**54.7 秒**完成。同樣的查詢從瀏覽器經 Codespaces 轉發網址送出，約 **100 秒**後回傳 **504**。
- **錯誤訊息**：

  ```text
  {待補：介面顯示的錯誤訊息（504）}
  ```

- **原因**：nginx 前面的連接埠轉發有自己的上限，nginx 與後端的 300 秒設定（ADR 0009）改變不了它。`/query` 要等整個回答完成才送出任何東西，所以連線會有一分鐘以上沒有任何資料。瀏覽器的請求為什麼比 `curl` 久（模型尚未載入、`top_k` 不同，或排在另一個請求後面）還沒有確認。{待補}
- **解法**：改為串流回答（ADR 0010）。後端馬上送出第一個事件，之後至少每 `STREAM_HEARTBEAT_SECONDS`（10 秒）送一次 heartbeat，接著送引用片段與 token，連線不會閒置。{待填：在 Codespaces 透過轉發網址實測串流查詢的結果}

### 問題 2：本機驗證發現，只開 `proxy_buffering on` 不會卡住串流，gzip 才會

- **問題**：為了確認冒煙測試抓得到會緩衝的代理，讓串流經過一個 `proxy_buffering on`（並忽略 `X-Accel-Buffering`）的 nginx。結果事件仍然一個一個到達，檢查永遠不會失敗。
- **錯誤訊息**：沒有；測試在應該失敗時通過了。
- **原因**：用戶端讀得夠快時，nginx 1.29 會盡快把緩衝的資料轉送出去。真正把串流卡住的是 **gzip**：對 `text/event-stream` 開啟 `gzip on` 後，一個 4 秒回答的 13 個 token 全部在最後同一瞬間到達。冒煙測試的 `curl` 沒有送出 `Accept-Encoding: gzip`，nginx 就不會壓縮，問題因此被隱藏。瀏覽器則一定會送出這個標頭。
- **解法**：串流的 location 除了 `proxy_buffering off`，也設定 `gzip off`。冒煙測試改用 `curl --compressed`，為每一行記下收到的時間；設定 `STREAM_STRICT=1`（CI）時，如果後端串流超過 1 秒、所有事件卻在 0.1 秒內到達，就判定失敗。用有問題的設定驗證過：`✗ All events arrived within 0.00s although the backend streamed for 4.321s.`

## 學到的概念

- **串流讓代理不會切斷連線**：定期送出資料的回應不會觸發閒置上限，使用者也看得到進度。見[知識檢核清單 §14](../learning/knowledge-checklist.md#14-server-sent-events-and-streaming-responses)。
- **緩衝與壓縮都會延遲串流**，測試用戶端必須和瀏覽器行為一致才發現得了。見 [§15](../learning/knowledge-checklist.md#15-reverse-proxy-buffering)。
- **`postStartCommand` 每次啟動都執行，`postCreateCommand` 只執行一次**：伺服器要放在前者。見 [§16](../learning/knowledge-checklist.md#16-dev-containers-and-codespaces)。
