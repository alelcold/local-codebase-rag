## Problems

### Problem 1: Group B looked twice as fast as the baseline, but hybrid search was not the reason

- **Problem**: B's mean first-token time on the main set was 6.7 s against A's 13.0 s, although hybrid search only adds a few milliseconds.
- **Error message**: none; per-question numbers from the JSON reports:

  ```text
  B (hybrid) first_token_seconds: Q2 0.189, Q4 0.268, Q9 0.185   (A: 16.975, 11.861, 14.953)
  retrieval_seconds mean: A 0.082, B 0.088
  ```

- **Cause**: For 7 of the 10 main questions, B retrieved exactly the same excerpts as A (hybrid rarely changes rankings without identifiers), so the prompt was identical. A first token after ~0.2 s means the prompt was not evaluated again, which points to Ollama reusing its cached prompt. Questions whose excerpts changed (5, 8) were not faster (11.7 → 13.9 s, 16.2 → 15.0 s).
- **Fix**: none in code. Footnote in `docs/metrics.md` §4a; latency comparisons between groups should be treated as indicative. For a clean latency comparison, restart Ollama (or run a different warm-up) between groups, or run each group twice in alternating order.

### Problem 2: `calibrate_threshold.py` listed the same reports as "skipped" and as "used"

- **Problem**: The calibration output named the hybrid reports twice: under 「略過」 and in the group's report list.
- **Error message** (output before the fix, abridged):

  ```text
  Skipped / 略過：
  - 2026-11-03-codespace-3b-k4-hybrid.json: no cosine scores (hybrid run written before vector_score existed?)
  ...
  Reports (6): `…-baseline-ident.json`, `…-baseline.json`, `…-hybrid-ident.json`, `…-hybrid.json`, `…-split-ident.json`, `…-split.json`
  ```

- **Cause**: `load_samples` added every report to the group's list *before* reading its excerpts, and only afterwards noted "no cosine scores" when nothing was added. The hybrid reports were written before `vector_score` existed, so they hold only RRF scores and contributed nothing; the "Skipped" note was right and the report list was wrong. The numbers were not affected (no samples came from those files).
- **Fix**: a report is added to the list only when it adds samples. Otherwise it is listed once under 「未使用的報告」, with the reason: no cosine scores, or all its excerpts were already counted from another report. Unit test: `test_calibrate_never_lists_a_report_as_both_skipped_and_used`.

## Threshold calibration: no usable `SCORE_THRESHOLD` on this data

From the A and C reports (main + identifier sets; B and F hold no cosine scores): 27 excerpts from an expected file, 63 from other files, 7 for the trick question.

| Excerpts | Cosine, median (min–max) |
| --- | --- |
| Expected file | 0.616 (0.487–0.745) |
| Other file | 0.604 (0.466–0.759) |
| Trick question (should be refused) | 0.542 (0.478–0.570) |

| Threshold | Expected excerpts dropped | Other excerpts blocked | Questions losing every expected excerpt | Trick refused |
| --- | --- | --- | --- | --- |
| ≤ 0.45 | 0/27 | 0/70 | 0 | 0/1 |
| 0.50 | 2/27 (7 %) | 10/70 (14 %) | 0 | 0/1 |
| 0.55 | 4/27 (15 %) | 18/70 (26 %) | 2 | 0/1 |
| 0.60 | 13/27 (48 %) | 36/70 (51 %) | 6 | 1/1 |
| **0.70** | **25/27 (93 %)** | 69/70 (99 %) | 10 | 1/1 |

- The distributions overlap: an excerpt's cosine does not say whether it is relevant. Every threshold either blocks nothing (≤ 0.45) or drops correct excerpts about as often as wrong ones.
- The commonly quoted 0.70 would drop **25 of 27 correct excerpts (93 %)** and leave 10 questions with no correct excerpt.
- The trick question is refused only from 0.60, where 6 real questions already lose all their correct excerpts.
- Decision: G not run, `SCORE_THRESHOLD` stays empty (ADR 0014 unchanged). A threshold cannot be calibrated for the metadata index either: F's reports have no cosine scores. Refusing the trick question needs another signal (rerank score, or the answer itself).

- **Rerank alone (H) does not help.** The cross-encoder can only reorder the 10 vector candidates, and for the main set those are almost all Markdown. Defining file (main) stays 0/3, docs 85%, and on the identifier set it goes from 1/3 to 2/3 (question 13 gained, question 11 still misses `gameConfig.ts`), below B and C (3/3), which change *which* candidates exist. It also prefers docs: Markdown sections got rerank scores of 0.8–0.99, code excerpts mostly < 0.1.
- **Hybrid + split + rerank (I) is the best retrieval so far.** Main-set defining file 3/3: question 1 finally retrieves `gameConfig.ts` (first place), question 8 `InputManager.ts`, question 9 `GameState.ts`. Q1's answer names `src/config/gameConfig.ts`, `INVINCIBLE_MS` and 1500 ms (keyword check only; correctness still to be judged).
- **Where the gain comes from (from `matched_by` and scores in the JSON):** Q8's `InputManager.ts` came from the keyword channel only (hybrid). Q1's `gameConfig.ts` and Q9's `GameState.ts` came from the vector channel: they were already among the code candidates, and rerank moved them into the 3 code slots. Their rerank scores are tiny (Q1: 0.0027 vs 0.0003 for the next code excerpt), so the ordering is fragile. D (hybrid + split without rerank) was not run, so this split of credit is read from one run, not measured.
- **Trick question:** no group refused it. In I, Q10's best rerank score was 0.33, while relevant docs score 0.8–0.99, but Q9 (a real question) had a best score of 0.0165. A rerank-score threshold would not separate them either.

First-token time is measured from the request, so it includes rerank: I vs C is +10.9 s, of which 4.8 s is rerank; the rest is longer prompts and run-to-run noise. Model download + first load (warm-up query of H): 57.9 s, once per volume.
- **Prompt cache again:** in I's identifier set, question 15 retrieved the same excerpts as in H and its first token minus rerank was 0.2 s, so that mean is too low.

## 遇到的問題

### 問題 1：B 組看起來比基準線快一倍，但原因不是混合檢索

- **問題**：B 組主要題組的首字延遲平均 6.7 秒，A 組 13.0 秒，但混合檢索只多花幾毫秒。
- **錯誤訊息**：沒有；以下是 JSON 報告中的每題數字：

  ```text
  B (hybrid) first_token_seconds: Q2 0.189, Q4 0.268, Q9 0.185   (A: 16.975, 11.861, 14.953)
  retrieval_seconds mean: A 0.082, B 0.088
  ```

- **原因**：主要題組 10 題中有 7 題，B 取回的片段與 A 完全相同（沒有識別字時混合檢索很少改變排名），提示也就完全相同。首字只要約 0.2 秒，代表提示沒有重新計算，看起來是 Ollama 重用了快取的提示。片段有改變的題目（5、8）沒有變快（11.7 → 13.9 秒、16.2 → 15.0 秒）。
- **解法**：不改程式。在 `docs/metrics.md` §4a 加註；各組之間的延遲比較只能當參考。要乾淨地比較延遲，各組之間重啟 Ollama（或用不同的暖機問題），或以交錯順序每組各跑兩次。

### 問題 2：`calibrate_threshold.py` 把同一份報告同時列為「略過」與「使用」

- **問題**：校準輸出中，混合檢索的報告出現兩次：在「略過」清單，也在該組的報告清單中。
- **錯誤訊息**（修正前的輸出，節錄）：

  ```text
  Skipped / 略過：
  - 2026-11-03-codespace-3b-k4-hybrid.json: no cosine scores (hybrid run written before vector_score existed?)
  ...
  Reports (6): `…-baseline-ident.json`, `…-baseline.json`, `…-hybrid-ident.json`, `…-hybrid.json`, `…-split-ident.json`, `…-split.json`
  ```

- **原因**：`load_samples` 在讀取片段*之前*就把報告加入清單，之後才在沒有新增任何樣本時記下「no cosine scores」。混合檢索的報告寫於 `vector_score` 出現之前，只有 RRF 分數，沒有貢獻任何樣本；「略過」是對的，報告清單是錯的。數據本身不受影響（這些檔案沒有產生樣本）。
- **解法**：只有實際新增樣本的報告才會列入清單；否則只在「未使用的報告」列一次並說明原因：沒有 cosine 分數，或所有片段都已由其他報告計入。單元測試：`test_calibrate_never_lists_a_report_as_both_skipped_and_used`。

## 門檻校準：這份資料上沒有可用的 `SCORE_THRESHOLD`

使用 A、C 組的報告（主要 + 識別字題組；B、F 沒有 cosine 分數）：預期檔案的片段 27 個、其他檔案 63 個、陷阱題 7 個。

| 片段 | Cosine 中位數（最小–最大） |
| --- | --- |
| 預期檔案 | 0.616（0.487–0.745） |
| 其他檔案 | 0.604（0.466–0.759） |
| 陷阱題（應拒答） | 0.542（0.478–0.570） |

| 門檻 | 丟掉的正確片段 | 擋掉的其他片段 | 失去所有正確片段的題目 | 陷阱題拒答 |
| --- | --- | --- | --- | --- |
| ≤ 0.45 | 0/27 | 0/70 | 0 | 0/1 |

| 0.60 | 13/27（48%） | 36/70（51%） | 6 | 1/1 |
| **0.70** | **25/27（93%）** | 69/70（99%） | 10 | 1/1 |

- 兩個分布重疊：片段的 cosine 分數無法判斷它是否相關。每個門檻不是什麼都擋不到（≤ 0.45），就是丟掉正確片段的比例和擋掉錯誤片段差不多。
- 常見的 0.70 會丟掉 **27 個正確片段中的 25 個（93%）**，讓 10 題完全沒有正確片段。
- 陷阱題要到 0.60 才會被拒答，而那時已有 6 題真正的問題失去所有正確片段。
- 決定：不執行 G 組，`SCORE_THRESHOLD` 維持空白（ADR 0014 不變）。metadata 索引也無法校準：F 的報告沒有 cosine 分數。要讓陷阱題拒答，需要別的訊號（rerank 分數，或回答本身）。

- **只開 Rerank（H）沒有幫助。** 交叉編碼器只能重排向量檢索的 10 個候選，而主要題組的候選幾乎都是 Markdown。定義檔命中（主要）仍是 0/3，文件比例 85%；識別字題組從 1/3 升到 2/3（第 13 題命中，第 11 題仍沒取回 `gameConfig.ts`），低於 B、C 的 3/3；B、C 改變的是「有哪些候選」。它也偏好文件：Markdown 段落的 rerank 分數 0.8–0.99，程式碼片段大多 < 0.1。
- **混合 + 分類 + Rerank（I）是目前最好的取回。** 主要題組定義檔命中 3/3：第 1 題終於取回 `gameConfig.ts`（排第一），第 8 題 `InputManager.ts`，第 9 題 `GameState.ts`。第 1 題的回答寫出 `src/config/gameConfig.ts`、`INVINCIBLE_MS` 與 1500 毫秒（只是關鍵字檢查，正確性仍待人工評分）。
- **改善來自哪裡（依 JSON 中的 `matched_by` 與分數）：** 第 8 題的 `InputManager.ts` 只由關鍵字通道找到（混合檢索）。第 1 題的 `gameConfig.ts` 與第 9 題的 `GameState.ts` 來自向量通道：它們原本就在程式碼候選中，是 rerank 把它們排進 3 個程式碼名額。它們的 rerank 分數非常小（第 1 題：0.0027，下一段程式碼 0.0003），排序並不穩定。D 組（混合 + 分類、不含 Rerank）沒有跑，所以這個功勞分配是從一次執行讀出來的，不是量測結果。
- **陷阱題：** 沒有任何一組拒答。I 組第 10 題最高 rerank 分數 0.33，相關文件 0.8–0.99，但第 9 題（真實問題）最高只有 0.0165，用 rerank 分數當門檻同樣分不開。
- **成本：** 在 4 核心 CPU 上每次查詢 rerank 2.0–6.7 秒，隨候選長度增加：I 組的候選多半是程式碼片段（比文件段落長），所以是 4.8 秒（主要）／6.4 秒（識別字），H 組 2.9 秒，與微基準測試的 10 組 3.7 秒（metrics §4b）相近。首字延遲從送出請求開始計算，包含 rerank：I 比 C 多 10.9 秒，其中 4.8 秒是 rerank，其餘是較長的提示與執行間的雜訊。模型下載＋第一次載入（H 組暖機查詢）：57.9 秒，每個 volume 一次。
- **又遇到提示快取：** I 組識別字題組第 15 題取回的片段與 H 組相同，首字延遲扣掉 rerank 只有 0.2 秒，所以該平均偏低。
