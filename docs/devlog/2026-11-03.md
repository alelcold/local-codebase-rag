# Devlog 2026-11-03 — Retrieval switch experiments (groups A, B, C, F)

> English first; 繁體中文版本在下方.
> Privacy: only the sample project (`examples/sample-game-frontend/`) was indexed and evaluated.

## What I did

- Ran groups A (baseline), B (`HYBRID_SEARCH`), C (`SPLIT_RETRIEVAL`, `DOC_TOP_K=1`) and F (all on, incl. `CHUNK_METADATA` and `PROMPT_VARIANT=v2`) from the [experiment plan](../evaluation/experiment-plan-retrieval.md) on Codespaces (CPU, `qwen2.5-coder:3b`, `TOP_K=4`). D and E were skipped.
- Each group: `./scripts/index.sh` with the group's variables (so the backend is recreated with them), then `/health` checked against the expected switches and `reindex_needed=false`, then `evaluate.py` on `questions.yaml` and `questions-identifiers.yaml`. All 8 runs: 0 errors. Afterwards the stack was put back to the baseline (`index.sh` without variables; `/health` checked).
- Index rebuilds happened where expected: A (first run after upgrading, 41.9 s, 67 chunks), F (`chunk_metadata=off` → `on`, 20.7 s), back to baseline (`on` → `off`, 18.8 s). B and C: nothing to re-index.
- `compare.py` for A→B, A→C, A→F, each for both question sets: `docs/evaluation/results/2026-11-03-baseline-vs-*.md`.
- Manual correctness is **not judged yet**; the 「人工判定正確性」 column in every report is empty and `docs/metrics.md` §4a keeps `{待填}` there.

- **Defining file**: on the identifier questions, both hybrid (B) and split (C) alone take it from 1/3 to 3/3. On the main (Chinese, no identifier) set, only split found one more (Q8 → `InputManager.ts`). Question 1 (`gameConfig.ts`, 無敵時間) was missed in every group, including F with chunk metadata: the `Defines: … INVINCIBLE_MS` header did not make 無敵 match `INVINCIBLE` for `nomic-embed-text`. F also lost the Q8 hit that C had (metadata changes the code embeddings).
- **Doc share**: split is what removes docs (95% → 25%, exactly the `DOC_TOP_K=1` cap). Hybrid alone barely changes the main set (95% → 88%) but halves it on the identifier set.
- **Simplified characters**: no switch fixes this. `PROMPT_VARIANT=v2` still produced 2 (Q4 `体`, Q8 `冲`). Split had the most (3); with mostly code in the prompt, the 3B model seems to drift to Simplified more often. B's 0 is within noise of A's 1.
- **v2 prompt**: answers are longer (241 vs 89 tokens) and start with `[n] path:lines` lists, which raises "cited with [n]" (0/9 → 4/9). Whether they are more correct is for the manual judging.
- **Latency**: retrieval takes 0.07–0.21 s in every group, so the switches cost nothing at retrieval time. First-token time follows prompt length: split/all retrieve longer code chunks (up to 146 lines; C Q3 47 s, F Q8 47 s). F's total time doubles because v2 answers are longer.

## Problems

### Problem 1: Group B looked twice as fast as the baseline, but hybrid search was not the reason

- **Problem**: B's mean first-token time on the main set was 6.7 s against A's 13.0 s, although hybrid search only adds a few milliseconds.
- **Error message**: none; per-question numbers from the JSON reports:

  ```text
  B (hybrid) first_token_seconds: Q2 0.189, Q4 0.268, Q9 0.185   (A: 16.975, 11.861, 14.953)
  retrieval_seconds mean: A 0.082, B 0.088
  ```

- **Cause**: For 7 of the 10 main questions, B retrieved exactly the same excerpts as A (hybrid rarely changes rankings without identifiers), so the prompt was identical. A first token after ~0.2 s means the prompt was not evaluated again, which points to Ollama reusing its cached prompt. Questions whose excerpts changed (5, 8) were not faster (11.7 → 13.9 s, 16.2 → 15.0 s).
- **Fix**: none in code. Footnote in `docs/metrics.md` §4a; latency comparisons between groups should be treated as indicative. For a clean latency comparison, restart Ollama (or run a different warm-up) between groups, or run each group twice in alternating order.

- **定義檔**：識別字題組上，混合（B）與分類（C）單獨開啟都能從 1/3 提升到 3/3。主要題組（中文、沒有識別字）只有分類取回多找到一題（第 8 題 → `InputManager.ts`）。第 1 題（`gameConfig.ts`，無敵時間）每一組都沒命中，包括開了 chunk metadata 的 F：`Defines: … INVINCIBLE_MS` 標頭沒有讓 `nomic-embed-text` 把「無敵」對應到 `INVINCIBLE`。F 還失去了 C 在第 8 題的命中（metadata 改變了程式碼的 embedding）。
- **文件比例**：降低文件比例的是分類取回（95% → 25%，正好是 `DOC_TOP_K=1` 的上限）。混合檢索單獨開啟時主要題組幾乎沒變（95% → 88%），識別字題組則減半。
- **簡體字**：沒有任何開關解決這個問題。`PROMPT_VARIANT=v2` 仍有 2 題（第 4 題 `体`、第 8 題 `冲`）。分類取回最多（3 題）；提示中多半是程式碼時，3B 模型似乎更容易轉成簡體。B 的 0 題與 A 的 1 題差距在雜訊範圍內。
- **v2 提示**：回答變長（241 vs 89 token），並以 `[n] 路徑:行號` 清單開頭，因此「以 [n] 引用」從 0/9 升到 4/9。是否更正確要等人工評分。
- **延遲**：每一組的檢索都只花 0.07–0.21 秒，開關本身在檢索階段幾乎沒有成本。首字延遲取決於提示長度：分類／全開會取回較長的程式碼片段（最多 146 行；C 第 3 題 47 秒、F 第 8 題 47 秒）。F 的總耗時加倍，因為 v2 的回答較長。

## 遇到的問題

### 問題 1：B 組看起來比基準線快一倍，但原因不是混合檢索

- **問題**：B 組主要題組的首字延遲平均 6.7 秒，A 組 13.0 秒，但混合檢索只多花幾毫秒。
- **錯誤訊息**：沒有；以下是 JSON 報告中的每題數字：

  ```text
  B (hybrid) first_token_seconds: Q2 0.189, Q4 0.268, Q9 0.185   (A: 16.975, 11.861, 14.953)
  retrieval_seconds mean: A 0.082, B 0.088
  ```

- **原因**：主要題組 10 題中有 7 題，B 取回的片段與 A 完全相同（沒有識別字時混合檢索很少改變排名），提示也就完全相同。首字只要約 0.2 秒，代表提示沒有重新計算，看起來是 Ollama 重用了快取的提示。片段有改變的題目（5、8）沒有變快（11.7 → 13.9 秒、16.2 → 15.0 秒）。
- **解法**：不改程式。在 `docs/metrics.md` §4a 加註；各組之間的延遲比較只能當參考。要乾淨地比較延遲，各組之間重啟 Ollama（或用不同的暖機問題），或以交錯順序每組各跑兩次。
