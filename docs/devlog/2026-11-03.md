## Problems

### Problem 1: Group B looked twice as fast as the baseline, but hybrid search was not the reason

- **Problem**: B's mean first-token time on the main set was 6.7 s against A's 13.0 s, although hybrid search only adds a few milliseconds.
- **Error message**: none; per-question numbers from the JSON reports:

  ```text
  B (hybrid) first_token_seconds: Q2 0.189, Q4 0.268, Q9 0.185   (A: 16.975, 11.861, 14.953)
  retrieval_seconds mean: A 0.082, B 0.088
  ```

- **Cause**: For 7 of the 10 main questions, B retrieved exactly the same excerpts as A (hybrid rarely changes rankings without identifiers), so the prompt was identical. A first token after ~0.2 s means the prompt was not evaluated again, which points to Ollama reusing its cached prompt. Questions whose excerpts changed (5, 8) were not faster (11.7 → 13.9 s, 16.2 → 15.0 s).
- **Fix**: none in code. Footnote in `docs/metrics.md` §4a; latency comparisons between groups should be treated as indicative. For a clean latency comparison, restart Ollama (or run a different warm-up) between groups, or run each group twice in alternating order.

### Problem 2: `calibrate_threshold.py` listed the same reports as "skipped" and as "used"

- **Problem**: The calibration output named the hybrid reports twice: under 「略過」 and in the group's report list.
- **Error message** (output before the fix, abridged):

  ```text
  Skipped / 略過：
  - 2026-11-03-codespace-3b-k4-hybrid.json: no cosine scores (hybrid run written before vector_score existed?)
  ...
  Reports (6): `…-baseline-ident.json`, `…-baseline.json`, `…-hybrid-ident.json`, `…-hybrid.json`, `…-split-ident.json`, `…-split.json`
  ```

- **Cause**: `load_samples` added every report to the group's list *before* reading its excerpts, and only afterwards noted "no cosine scores" when nothing was added. The hybrid reports were written before `vector_score` existed, so they hold only RRF scores and contributed nothing; the "Skipped" note was right and the report list was wrong. The numbers were not affected (no samples came from those files).
- **Fix**: a report is added to the list only when it adds samples. Otherwise it is listed once under 「未使用的報告」, with the reason: no cosine scores, or all its excerpts were already counted from another report. Unit test: `test_calibrate_never_lists_a_report_as_both_skipped_and_used`.

### Problem 3: `git push` from the codespace failed because of a Git LFS hook without `git-lfs`

- **Problem**: In the codespace, `git push` was refused before anything was sent, although the repository does not use Git LFS (no `.gitattributes`, no LFS files).
- **Error message** (printed by the Git LFS `pre-push` hook):

  ```text
  This repository is configured for Git LFS but 'git-lfs' was not found on your path. If you no longer wish to use Git LFS, remove this hook by deleting the 'pre-push' file in the hooks directory (set by 'core.hookspath'; usually '.git/hooks').
  ```

- **Cause**: The clone had Git LFS hooks in `.git/hooks/` (`pre-push` and friends, which call `git lfs …`), but the dev container image (`mcr.microsoft.com/devcontainers/base:ubuntu-24.04`) does not include the `git-lfs` binary and `post-create.sh` did not install it. The hook exits with an error when `git-lfs` is missing, and a failing `pre-push` hook aborts the push.
- **Fix**: `.devcontainer/post-create.sh` installs `git-lfs` together with `jq`, `zstd` and `iproute2`, then runs `git lfs install --skip-repo`. Plain `git lfs install` exits 2 (`Hook already exists: pre-push … run git lfs update --manual`) when the hooks are already there, which would stop the script under `set -e`; `--skip-repo` only sets the global filter config. `scripts/doctor.sh` has a new check 12 that looks for LFS hooks and fails, with the install command (and, since the repo has no LFS files, the alternative of deleting the hook), when `git-lfs` is missing. For an existing codespace: `sudo apt-get update && sudo apt-get install -y git-lfs`, or rebuild the container.

### Problem 4: The backend would not start with `PROMPT_VARIANT=v3`

- **Problem**: For group J, `docker compose up -d backend` with `PROMPT_VARIANT=v3` left the backend in `Restarting (1)`, and `/health` returned nothing.
- **Error message** (`docker compose logs backend`):

  ```text
  pydantic_core._pydantic_core.ValidationError: 1 validation error for Settings
  prompt_variant
    Value error, PROMPT_VARIANT must be one of ['v1', 'v2'], got 'v3' [type=value_error, input_value='v3', input_type=str]
  ```

- **Cause**: The backend image was built at 16:06 (+0800) for groups H and I. The code is copied into the image, not mounted. `PROMPT_VARIANT=v3` (#14) was merged at 17:24, so the running image did not know v3. The source was correct: only `app/config.py` and `app/rag.py` differed between the image and `HEAD`, and #14 changed only the prompt there (`PROMPT_VARIANTS`, the v3 text and its `build_prompt` branch). The v1 path, retrieval and indexing were unchanged, so D's control run on the old image stays comparable.
- **Fix**: `docker compose build backend` (default `INSTALL_RERANK=false`, no rerank image), then recreated the backend with J's variables. `/health` then showed `prompt_variant: v3`. No code or `.env` changes. After merging backend code, rebuild the image before running an experiment. `/health` catches this because the backend fails to start, but a change that does not fail at startup would go unnoticed.

## Threshold calibration: no usable `SCORE_THRESHOLD` on this data

From the A and C reports (main + identifier sets; B and F hold no cosine scores): 27 excerpts from an expected file, 63 from other files, 7 for the trick question.

| Excerpts | Cosine, median (min–max) |
| --- | --- |
| Expected file | 0.616 (0.487–0.745) |
| Other file | 0.604 (0.466–0.759) |
| Trick question (should be refused) | 0.542 (0.478–0.570) |

| Threshold | Expected excerpts dropped | Other excerpts blocked | Questions losing every expected excerpt | Trick refused |
| --- | --- | --- | --- | --- |
| ≤ 0.45 | 0/27 | 0/70 | 0 | 0/1 |
| 0.50 | 2/27 (7 %) | 10/70 (14 %) | 0 | 0/1 |
| 0.55 | 4/27 (15 %) | 18/70 (26 %) | 2 | 0/1 |
| 0.60 | 13/27 (48 %) | 36/70 (51 %) | 6 | 1/1 |
| **0.70** | **25/27 (93 %)** | 69/70 (99 %) | 10 | 1/1 |

- The distributions overlap: an excerpt's cosine does not say whether it is relevant. Every threshold either blocks nothing (≤ 0.45) or drops correct excerpts about as often as wrong ones.
- The commonly quoted 0.70 would drop **25 of 27 correct excerpts (93 %)** and leave 10 questions with no correct excerpt.
- The trick question is refused only from 0.60, where 6 real questions already lose all their correct excerpts.
- Decision: G not run, `SCORE_THRESHOLD` stays empty (ADR 0014 unchanged). A threshold cannot be calibrated for the metadata index either: F's reports have no cosine scores. Refusing the trick question needs another signal (rerank score, or the answer itself).

- **Rerank alone (H) does not help.** The cross-encoder can only reorder the 10 vector candidates, and for the main set those are almost all Markdown. Defining file (main) stays 0/3, docs 85%, and on the identifier set it goes from 1/3 to 2/3 (question 13 gained, question 11 still misses `gameConfig.ts`), below B and C (3/3), which change *which* candidates exist. It also prefers docs: Markdown sections got rerank scores of 0.8–0.99, code excerpts mostly < 0.1.
- **Hybrid + split + rerank (I) is the best retrieval so far.** Main-set defining file 3/3: question 1 finally retrieves `gameConfig.ts` (first place), question 8 `InputManager.ts`, question 9 `GameState.ts`. Q1's answer names `src/config/gameConfig.ts`, `INVINCIBLE_MS` and 1500 ms (keyword check only; correctness still to be judged).
- **Where the gain comes from (from `matched_by` and scores in the JSON):** Q8's `InputManager.ts` came from the keyword channel only (hybrid). Q1's `gameConfig.ts` and Q9's `GameState.ts` came from the vector channel: they were already among the code candidates, and rerank moved them into the 3 code slots. Their rerank scores are tiny (Q1: 0.0027 vs 0.0003 for the next code excerpt), so the ordering is fragile. D (hybrid + split without rerank) was not run at this point; it was run later and corrects this reading (see "Group D" below).

That is about the micro-benchmark's 3.7 s for 10 pairs (metrics §4b). First-token time is measured from the request, so it includes rerank: I vs C is +10.9 s, of which 4.8 s is rerank; the rest is longer prompts and run-to-run noise. Model download + first load (warm-up query of H): 57.9 s, once per volume.
- **Prompt cache again:** in I's identifier set, question 15 retrieved the same excerpts as in H and its first token minus rerank was 0.2 s, so that mean is too low.

- **On the main set, the whole defining-file gain of I comes from rerank.** D (hybrid + split without rerank) retrieves 0/3, so hybrid on top of split adds nothing here, and D → I is 0/3 → 3/3.
  - Q1 (`gameConfig.ts`) and Q9 (`GameState.ts`): D retrieved exactly the same excerpts as C (vector channel only; the Chinese questions give BM25 nothing to match). The files were among the code candidates, and rerank moved them into the top 3 code slots.
  - Q8 (`InputManager.ts`): C had it (vector). In D, RRF ranked candidates found by both vector and keyword (`Player.ts`, `Hud.tsx`, `Game.ts`) above it, so hybrid *pushed it out*. In I, rerank brought it back as the first code excerpt; in that run it came from the keyword channel only. So in I, Q8 depended on hybrid to make it a candidate and on rerank to choose it, while C (split only) got it with neither.
  - This corrects the reading in the Rerank section above, which credited Q8 to hybrid.
- **On the identifier set rerank adds nothing**: C, D and I are all 3/3. With rerank, "cited with [n]" drops (4/5 → 2/5) and keyword hit rate drops slightly (83% → 77%).
- **Rerank is fragile here**: the code excerpts it promotes score 0.0027 (Q1) and 0.0738 (Q8) against 0.0003–0.03 for the other code excerpts. The gain is on 3 questions from one run each.
- **Cost of the gain**: rerank 4.8 s per query (main), and first token +9.6 s D → I (26.8 vs 17.2 s); hybrid itself costs milliseconds (C → D first token +1.3 s, within noise).
- **Simplified characters**: D 4 / 2, I 0 / 0. Prompts differ only in which excerpts are included, so this looks like excerpt-dependent model behaviour rather than an effect of rerank; not something to attribute to rerank from one run.
- **Not measured**: split + rerank without hybrid (C + rerank). Since hybrid did not help the main set in D, that combination may give I's main-set result at the same rerank cost. Worth one run before choosing between D and I as a default.

J = D + `PROMPT_VARIANT=v3` (labels `codespace-3b-k4-hybrid-split-v3[-ident|-oos]`). First the control run: D with prompt v1 on `questions-out-of-scope.yaml` (`codespace-3b-k4-hybrid-split-oos`). - **v3 does not tell real questions from trick questions.** 19 of 23 answers are exactly 「在索引的專案中找不到相關內容。」 (11 tokens). Only main Q3 (game loop) and ident. Q12, Q14, Q15 were answered.
- **Real questions were refused even when the right code was retrieved.** Main Q5 (2/2 expected files retrieved), Q6 (3/4), Q8 (D answered with 4/5 keywords), and ident. Q11 / Q13 got the fixed sentence. In Q11 and Q13 the identifier from the question (`INVINCIBLE_MS`, `DASH_COOLDOWN_MS`) appears verbatim in a retrieved excerpt. Main Q1, Q2 and Q4 retrieved none of their expected code, so "not found" there matches what the model saw. That is a retrieval problem, and the answer still misleads the user.
- **All three control questions (26–28) were refused**: high score saving, sound and focus loss, which are exactly the cases the set was built to catch.
- **No Simplified characters, but this proves little**: 19 answers are a fixed Traditional sentence. The 4 real answers had none, too few to credit rule 5.
- **Latency**: first token does not drop, because the whole prompt is still evaluated before the model writes the refusal. Total time drops by about 3 s on the main set because the answers are short. First-token differences between D and J are noisy: D's Q5 and Q7 (7.0 s, 8.5 s) look like prompt-cache hits (Problem 1).
- **Why (hypothesis, not tested)**: the refusal is the shortest, safest completion, and the reminder 「(If no excerpt directly mentions this topic, reply only: …)」 is the last thing the 3B model reads before `## Answer`. "Directly mentions the topic" is a judgement the 3B model does not make reliably. Ideas for a v4, not run: drop the trailing reminder, or tie the rule to something checkable (the question's identifier or file is in no excerpt). v3 on `qwen2.5-coder:14b` (Mac) is also untested; the failure may be specific to 3B.
- **Scoring caveats found while reading D's answers**: Q22 「我无法提供…」 is a refusal written in Simplified, and the trick keywords list 無法 but not 无法, so it scored "not refused". Q28 「没有直接处理…的逻辑」 is wrong, but a bare 没有 is deliberately not a refusal phrase, so it is not a false refusal. Q23 (cloud sync "via `syncUi`") and Q25 (gamepad mapped to the keyboard handler) are invented answers that pass as "not refused, no forbidden word". The keyword screen undercounts D's refusals by one. J's numbers are unaffected: its refusals are the exact fixed sentence.
- **Decision**: per the plan's rule (false refusal rate 0 on every set), **v3 is not adopted**. `PROMPT_VARIANT` stays `v1`; `.env.codespaces` and `.env.example` are unchanged. No ADR, because no default changes. ADR 0016 stays accepted as an optional variant.

## 遇到的問題

### 問題 1：B 組看起來比基準線快一倍，但原因不是混合檢索

- **問題**：B 組主要題組的首字延遲平均 6.7 秒，A 組 13.0 秒，但混合檢索只多花幾毫秒。
- **錯誤訊息**：沒有；以下是 JSON 報告中的每題數字：

  ```text
  B (hybrid) first_token_seconds: Q2 0.189, Q4 0.268, Q9 0.185   (A: 16.975, 11.861, 14.953)
  retrieval_seconds mean: A 0.082, B 0.088
  ```

- **原因**：主要題組 10 題中有 7 題，B 取回的片段與 A 完全相同（沒有識別字時混合檢索很少改變排名），提示也就完全相同。首字只要約 0.2 秒，代表提示沒有重新計算，看起來是 Ollama 重用了快取的提示。片段有改變的題目（5、8）沒有變快（11.7 → 13.9 秒、16.2 → 15.0 秒）。
- **解法**：不改程式。在 `docs/metrics.md` §4a 加註；各組之間的延遲比較只能當參考。要乾淨地比較延遲，各組之間重啟 Ollama（或用不同的暖機問題），或以交錯順序每組各跑兩次。

### 問題 2：`calibrate_threshold.py` 把同一份報告同時列為「略過」與「使用」

- **問題**：校準輸出中，混合檢索的報告出現兩次：在「略過」清單，也在該組的報告清單中。
- **錯誤訊息**（修正前的輸出，節錄）：

  ```text
  Skipped / 略過：
  - 2026-11-03-codespace-3b-k4-hybrid.json: no cosine scores (hybrid run written before vector_score existed?)
  ...
  Reports (6): `…-baseline-ident.json`, `…-baseline.json`, `…-hybrid-ident.json`, `…-hybrid.json`, `…-split-ident.json`, `…-split.json`
  ```

- **原因**：`load_samples` 在讀取片段*之前*就把報告加入清單，之後才在沒有新增任何樣本時記下「no cosine scores」。混合檢索的報告寫於 `vector_score` 出現之前，只有 RRF 分數，沒有貢獻任何樣本；「略過」是對的，報告清單是錯的。數據本身不受影響（這些檔案沒有產生樣本）。
- **解法**：只有實際新增樣本的報告才會列入清單；否則只在「未使用的報告」列一次並說明原因：沒有 cosine 分數，或所有片段都已由其他報告計入。單元測試：`test_calibrate_never_lists_a_report_as_both_skipped_and_used`。

### 問題 3：codespace 裡 `git push` 失敗，因為有 Git LFS hook 卻沒有 `git-lfs`

- **問題**：在 codespace 中執行 `git push`，還沒送出任何資料就被拒絕；但本 repo 根本沒有使用 Git LFS（沒有 `.gitattributes`，也沒有 LFS 檔案）。
- **錯誤訊息**（Git LFS 的 `pre-push` hook 印出）：

  ```text
  This repository is configured for Git LFS but 'git-lfs' was not found on your path. If you no longer wish to use Git LFS, remove this hook by deleting the 'pre-push' file in the hooks directory (set by 'core.hookspath'; usually '.git/hooks').
  ```

- **原因**：clone 下來的 `.git/hooks/` 裡有 Git LFS 的 hook（`pre-push` 等，會呼叫 `git lfs …`），但 dev container 的映像檔（`mcr.microsoft.com/devcontainers/base:ubuntu-24.04`）沒有 `git-lfs`，`post-create.sh` 也沒有安裝。找不到 `git-lfs` 時 hook 會以錯誤結束，而 `pre-push` hook 失敗就會中止 push。
- **解法**：`.devcontainer/post-create.sh` 與 `jq`、`zstd`、`iproute2` 一起安裝 `git-lfs`，接著執行 `git lfs install --skip-repo`。hook 已存在時，單純的 `git lfs install` 會以結束碼 2 結束（`Hook already exists: pre-push … run git lfs update --manual`），在 `set -e` 下會讓腳本中斷；`--skip-repo` 只設定全域的 filter。`scripts/doctor.sh` 新增第 12 項檢查：有 LFS hook 但沒有 `git-lfs` 時判定失敗，並印出安裝指令（因為本 repo 沒有 LFS 檔案，也列出刪除 hook 的替代做法）。已經建立的 codespace：`sudo apt-get update && sudo apt-get install -y git-lfs`，或 Rebuild Container。

### 問題 4：設定 `PROMPT_VARIANT=v3` 後 backend 無法啟動

- **主要題組上，I 組定義檔命中的改善全部來自 Rerank。** D（混合 + 分類、不含 Rerank）是 0/3，混合檢索加在分類取回上這裡沒有幫助；D → I 是 0/3 → 3/3。
  - 第 1 題（`gameConfig.ts`）與第 9 題（`GameState.ts`）：D 取回的片段與 C 完全相同（只有向量通道；中文問題讓 BM25 沒有可比對的字）。檔案本來就在程式碼候選中，是 rerank 把它們排進前 3 個程式碼名額。
  - 第 8 題（`InputManager.ts`）：C 有取回（向量）。D 中 RRF 把向量與關鍵字都找到的候選（`Player.ts`、`Hud.tsx`、`Game.ts`）排在它前面，混合檢索反而*把它擠掉*。I 中 rerank 又把它排成第一段程式碼；那次它只由關鍵字通道找到。所以在 I 組，第 8 題要靠混合檢索成為候選、再靠 rerank 被選上；而 C（只有分類取回）兩者都不用就取回了。
  - 這修正了上方 Rerank 段落把第 8 題歸功於混合檢索的解讀。

- **簡體字**：D 4／2，I 0／0。兩組提示的差別只在選了哪些片段，看起來是隨片段而變的模型行為，不能從一次執行就歸功於 rerank。
- **尚未量測**：分類取回 + Rerank、不含混合檢索（C + Rerank）。D 顯示混合檢索對主要題組沒有幫助，這個組合可能以相同的 rerank 成本得到 I 在主要題組的結果。在 D、I 之間選預設值之前，值得再跑一次。

- **正確的程式碼已經取回，仍然被拒答。** 主要題組第 5 題（預期檔案 2/2 都有取回）、第 6 題（3/4）、第 8 題（D 組回答命中 4/5 關鍵字），以及識別字題組第 11、13 題都只回固定句。第 11、13 題題目中的識別字（`INVINCIBLE_MS`、`DASH_COOLDOWN_MS`）原封不動出現在取回的片段裡。主要題組第 1、2、4 題沒有取回任何預期的程式碼，所以「找不到」與模型看到的內容一致；那是檢索的問題，但這個回答仍然會誤導使用者。

- **讀 D 組回答時發現的計分問題**：第 22 題「我无法提供…」是用簡體字寫的拒答，陷阱題關鍵字只有「無法」、沒有「无法」，所以被判為「未拒答」。第 28 題「没有直接处理…的逻辑」是錯的，但單獨的「没有」刻意不算拒答字句，所以不算誤拒。第 23 題（「透過 `syncUi`」同步到雲端）與第 25 題（把手把對應到鍵盤處理函式）是編造的回答，卻以「未拒答、無禁用字」通過。關鍵字篩選少算了 D 組 1 題拒答；J 組不受影響，因為它的拒答都是完全相同的固定句。
- **決定**：依實驗計畫的規則（每個題組的誤拒率都必須是 0），**不採用 v3**。`PROMPT_VARIANT` 維持 `v1`，`.env.codespaces` 與 `.env.example` 不變。預設值沒有改變，所以不新增 ADR；ADR 0016 仍是已接受的可選提示版本。
